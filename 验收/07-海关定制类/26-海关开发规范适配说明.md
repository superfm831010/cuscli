## 1. 概述

### 1.1 文档目的

本文档说明Auto-Coder AI代码检查系统如何适配海关总署的开发规范要求，帮助海关开发团队配置符合海关标准的代码检查规则。

**主要目标：**
- 理解海关开发规范的核心要求
- 掌握规则配置方法
- 确保生成代码符合海关标准
- 提供可复用的配置模板

### 1.2 适用范围

**适用对象：**
- 海关系统架构师
- 海关开发规范制定者
- Auto-Coder系统配置管理员
- 开发团队负责人

**适用场景：**
- 初始规则配置
- 规范更新后的规则调整
- 新项目的规则定制
- 代码质量审查

### 1.3 海关开发特点

| 特点 | 说明 | 影响 |
|------|------|------|
| **标准化要求高** | 严格的编码规范和架构标准 | 需要精确的规则配置 |
| **安全性要求** | 高安全等级要求 | 需要专门的安全检查规则 |
| **统一技术栈** | 统一的开发框架和技术体系 | 规则可标准化配置 |
| **审核严格** | 代码需要通过多级审核 | 需要完整的符合性报告 |

## 2. 海关开发规范体系

### 2.1 规范分类

海关开发规范通常包含以下几个方面：

| 规范类别 | 主要内容 | 优先级 |
|---------|---------|--------|
| **架构规范** | 系统架构、分层设计、模块划分 | 🔴 高 |
| **编码规范** | 命名规则、代码风格、注释要求 | 🔴 高 |
| **安全规范** | 安全编码、权限控制、数据保护 | 🔴 高 |
| **接口规范** | API设计、接口文档、数据格式 | 🟡 中 |
| **数据库规范** | 表设计、索引、SQL编写 | 🟡 中 |
| **测试规范** | 单元测试、集成测试、覆盖率 | 🟡 中 |
| **文档规范** | 代码注释、设计文档、接口文档 | 🟢 低 |

### 2.2 规范框架概览

```
海关开发规范体系
    │
    ├── 技术架构规范
    │   ├── 分层架构要求
    │   ├── 微服务设计规范
    │   └── 组件使用规范
    │
    ├── 编码标准规范
    │   ├── 命名规范
    │   ├── 代码格式规范
    │   └── 异常处理规范
    │
    ├── 安全开发规范
    │   ├── 身份认证规范
    │   ├── 权限控制规范
    │   └── 数据安全规范
    │
    ├── 接口开发规范
    │   ├── RESTful规范
    │   ├── 接口文档规范
    │   └── 版本管理规范
    │
    └── 数据库开发规范
        ├── 表设计规范
        ├── SQL编写规范
        └── 性能优化规范
```

### 2.3 关键规范要点

#### 2.3.1 架构规范要点

| 要点 | 说明 |
|------|------|
| 分层架构 | 严格的表示层、业务层、数据层分离 |
| 组件化 | 功能模块组件化、可复用设计 |
| 统一框架 | 基于特定开发框架构建 |
| 配置管理 | 配置与代码分离 |

#### 2.3.2 安全规范要点

| 要点 | 说明 |
|------|------|
| 输入验证 | 所有外部输入必须验证 |
| 输出编码 | 输出数据进行安全编码 |
| 权限控制 | 基于角色的访问控制(RBAC) |
| 日志审计 | 关键操作必须记录审计日志 |
| 敏感数据 | 敏感信息加密存储和传输 |

#### 2.3.3 编码规范要点

| 要点 | 说明 |
|------|------|
| 命名规范 | 类名、方法名、变量名遵循统一规则 |
| 注释规范 | 类、方法必须有完整注释 |
| 代码复杂度 | 方法复杂度有明确限制 |
| 异常处理 | 统一的异常处理机制 |

## 3. 规则配置适配

### 3.1 配置文件结构

Auto-Coder的海关规范适配主要通过`rules/rules_config.json`配置文件实现。

**配置文件结构：**
```json
{
  "rules_categories": [
    {
      "category": "架构规范",
      "priority": "high",
      "rules": [...]
    },
    {
      "category": "安全规范",
      "priority": "high",
      "rules": [...]
    }
  ],
  "check_settings": {
    "enabled_categories": [],
    "severity_threshold": "warning"
  }
}
```

### 3.2 规则配置方法

#### 3.2.1 规则定义框架

每条规则包含以下要素：

| 要素 | 说明 | 示例 |
|------|------|------|
| **规则ID** | 唯一标识 | `ARCH-001` |
| **规则名称** | 规则简要说明 | "分层架构检查" |
| **严重级别** | error/warning/info | `error` |
| **检查内容** | 具体检查项 | "检查是否违反分层原则" |
| **提示词** | LLM检查提示 | 引导AI进行检查 |

#### 3.2.2 配置适配流程

```
梳理海关规范要求
    ↓
识别可自动检查的规则
    ↓
编写规则配置
    ↓
设计检查提示词
    ↓
测试规则有效性
    ↓
调优规则参数
    ↓
正式部署应用
```

### 3.3 规则分类适配

#### 3.3.1 架构规范适配

**适配重点：**
- 分层架构合规性
- 模块依赖关系
- 组件使用规范
- 设计模式应用

**配置方向：**
| 检查项 | 配置方法 |
|-------|---------|
| 层次划分 | 配置分层规则，检查跨层调用 |
| 包结构 | 定义标准包结构规范 |
| 依赖管理 | 检查循环依赖、非法依赖 |
| 接口设计 | 验证接口设计规范 |

#### 3.3.2 安全规范适配

**适配重点：**
- SQL注入防护
- XSS防护
- 权限控制检查
- 敏感信息处理

**配置方向：**
| 检查项 | 配置方法 |
|-------|---------|
| 输入验证 | 检查是否对用户输入进行验证 |
| SQL安全 | 检查SQL拼接方式 |
| 权限控制 | 检查接口是否有权限注解 |
| 敏感数据 | 检查敏感信息是否加密 |

#### 3.3.3 编码规范适配

**适配重点：**
- 命名规范
- 代码格式
- 注释完整性
- 异常处理

**配置方向：**
| 检查项 | 配置方法 |
|-------|---------|
| 命名检查 | 定义命名模式规则 |
| 注释检查 | 要求类和方法必须有注释 |
| 代码复杂度 | 设置复杂度阈值 |
| 异常处理 | 检查try-catch使用 |

## 4. 代码检查规则定制

### 4.1 规则编写原则

| 原则 | 说明 |
|------|------|
| **明确性** | 规则描述清晰、无歧义 |
| **可检测性** | 规则可通过代码分析检测 |
| **适度性** | 规则严格程度适中 |
| **可理解性** | 开发人员能理解规则意图 |
| **可操作性** | 违规后有明确的修正方法 |

### 4.2 提示词设计

提示词是引导LLM进行代码检查的关键。

#### 4.2.1 提示词结构

**标准提示词包含：**
1. **检查目标**：明确要检查什么
2. **检查标准**：符合什么标准算合规
3. **检查方法**：如何进行检查
4. **输出要求**：期望的检查结果格式

#### 4.2.2 提示词示例框架

```
角色定位：
你是一个海关系统代码审查专家，熟悉海关开发规范。

检查任务：
检查以下代码是否符合[具体规范名称]。

检查要点：
1. [检查点1]
2. [检查点2]
3. [检查点3]

判断标准：
- 符合条件：[描述]
- 不符合条件：[描述]

输出格式：
- 符合性：是/否
- 问题描述：[如果不符合，描述问题]
- 建议：[改进建议]
```

### 4.3 规则优先级设置

#### 4.3.1 优先级分类

| 级别 | 定义 | 处理方式 |
|------|------|---------|
| **Error** | 严重违反规范，必须修复 | 阻止代码合并 |
| **Warning** | 违反规范，建议修复 | 给出警告，允许合并 |
| **Info** | 不符合最佳实践 | 仅提示，不影响合并 |

#### 4.3.2 优先级分配原则

**Error级别：**
- 安全规范违反
- 架构规范重大违反
- 可能导致系统故障的问题

**Warning级别：**
- 编码规范违反
- 性能问题
- 可维护性问题

**Info级别：**
- 代码风格问题
- 注释不完整
- 可读性建议

## 5. 符合性验证

### 5.1 验证流程

```
配置规则
    ↓
选择测试代码
    ↓
执行代码检查
    ↓
分析检查结果
    ↓
验证准确性
    ↓
调整规则配置
    ↓
重新验证
    ↓
确认规则有效
```

### 5.2 验证方法

#### 5.2.1 正向验证

**目的：** 验证符合规范的代码能通过检查

**步骤：**
1. 准备符合规范的示例代码
2. 执行代码检查
3. 确认检查结果为"通过"
4. 记录验证结果

#### 5.2.2 反向验证

**目的：** 验证违反规范的代码能被检测出来

**步骤：**
1. 准备违反规范的示例代码
2. 执行代码检查
3. 确认检查结果识别出问题
4. 验证问题描述的准确性

#### 5.2.3 边界验证

**目的：** 验证规则在边界情况下的表现

**验证场景：**
- 最小复杂度代码
- 最大复杂度代码
- 特殊语法结构
- 框架特定用法

### 5.3 验证记录

**验证记录表：**

| 规则ID | 验证类型 | 测试代码 | 预期结果 | 实际结果 | 是否通过 |
|-------|---------|---------|---------|---------|---------|
| ARCH-001 | 正向 | 符合分层的代码 | 通过 | 通过 | ✅ |
| ARCH-001 | 反向 | 跨层调用代码 | 检测出问题 | 检测出问题 | ✅ |
| SEC-001 | 正向 | 使用参数化查询 | 通过 | 通过 | ✅ |
| SEC-001 | 反向 | SQL拼接代码 | 检测出问题 | 检测出问题 | ✅ |

## 7. 最佳实践

### 7.1 配置管理最佳实践

| 实践 | 说明 |
|------|------|
| **版本控制** | 规则配置文件纳入版本控制 |
| **分层配置** | 全局配置+项目配置 |
| **定期审查** | 定期审查和更新规则 |
| **文档同步** | 配置与文档保持同步 |
| **测试验证** | 规则变更后充分测试 |

### 7.2 规则制定最佳实践

#### 7.2.1 规则粒度

**建议：**
- 规则不宜过细，保持适当抽象层次
- 一条规则关注一个方面
- 避免规则之间重叠

**示例：**
- ✅ 好：分层架构检查（检查是否违反分层原则）
- ❌ 差：Controller不能调用DAO（过于具体）

#### 7.2.2 提示词设计

**建议：**
- 提示词清晰具体
- 提供明确的判断标准
- 包含正反例说明
- 要求结构化输出

#### 7.2.3 优先级设置

**建议：**
- Error级别慎重设置
- 新规则从Warning开始
- 逐步提升严格程度
- 基于团队反馈调整

### 7.3 实施推广最佳实践

#### 7.3.1 渐进式推进

**阶段1：试点验证**
- 选择1-2个项目试点

- 收集反馈

**阶段2：优化完善**
- 根据反馈调整规则

- 增加更多规则

**阶段3：全面推广**
- 制定统一规范
- 全员培训
- 全面应用

### 7.4 持续改进

- 代码审查结果
- 检查准确率统计
- 规范变更通知

#### 7.4.2 规则优化

**优化方向：**
- 减少误报
- 提高检测准确性
- 完善规则描述
- 优化提示词

#### 7.4.3 版本管理

**建议：**
```
规则配置版本号：X.Y.Z
X - 主版本号（规范大版本变更）
Y - 次版本号（新增规则分类）
Z - 修订号（规则优化和修复）

示例：
1.0.0 - 初始版本
1.1.0 - 新增数据库规范
1.1.1 - 优化SQL注入检查规则
```
